# 农户资源提交流程设计与 E2E 用例（设计阶段 v0.1）

> 当前处于**设计阶段**：交付流程设计、状态机、权限规则与 E2E 用例；真实农户激活与 10–20 户验证属于实现/试运行阶段，不作为本阶段门禁。
> 关联：REQ-2026-009；数据口径见《数据资产与许可登记》。

## 一、流程设计

角色：农户（提交者）、入库员 keeper（审核）、审计员 auditor（抽查与留痕）、管理员 admin（配置）。

1. 短信登录，首次进入引导页；
2. 选择提交类型：地块 / 产品 / 服务；
3. 填写最小字段：
   - 地块：村组、面积、主要作物；
   - 产品：名称、品类、上市季节；
   - 服务：类型、服务范围、可服务时间；
4. 可选辅助录入：语音转写、拍照识别预填（实现阶段提供）；
5. 保存草稿（可多次编辑）；
6. 提交 → 状态进入待审核；
7. keeper 审核：通过 / 驳回（必须填写原因）；
8. 驳回后农户补充并重新提交；
9. 通过后进入业务库，可发布、接单、参与溯源；
10. 后续变更或删除走申请流程，保留审计记录。

## 二、状态机

```
draft（草稿）
  → submitted（已提交）
  → under_review（审核中）
      → approved（通过）→ active（可用）
      → rejected（驳回）→ draft（可修改后重提）
active → change_pending（变更申请）→ active
active → delete_pending（删除申请）→ deleted（保留审计）
```

规则：

- 只有归属农户可编辑 draft；
- keeper 不能审核自己提交的数据；
- auditor 只读 + 抽查，不参与日常审核；
- 提交必须幂等（同一草稿重复提交不产生多条记录）；
- 所有状态跃迁写入审计事件。

## 三、数据与权限

| 项 | 规则 |
| --- | --- |
| 行级权限 | 农户只能看自己的记录；keeper 按村组范围；auditor 全量只读 |
| 字段 | 最小字段可提交；发布/接单前校验完整度 |
| 脱敏 | 手机号、住址等界面脱敏，导出需审批 |
| 审计 | 提交、审核、驳回、变更、删除全部留痕 |
| 并发 | 版本号校验，冲突时提示重新加载 |

## 四、E2E 用例（P0）

| 编号 | 场景 | 前置条件 | 关键步骤 | 预期结果 |
| --- | --- | --- | --- | --- |
| E2E-01 | 新农户提交地块 | 农户已登录、无地块 | 填写最小字段 → 提交 | 状态为 under_review，生成一条记录 |
| E2E-02 | 必填字段缺失 | 同上 | 漏填面积 → 提交 | 阻止提交并提示具体字段 |
| E2E-03 | 审核通过 | 存在待审记录 | keeper 审核通过 | 状态 active，农户可见，审计有记录 |
| E2E-04 | 审核驳回后重提 | 存在待审记录 | 驳回并填原因 → 农户补充 → 重提 | 状态回到 under_review，原因可见 |
| E2E-05 | 越权访问 | 农户 A、B 各有记录 | A 访问 B 的记录 | 拒绝访问，返回无权限 |
| E2E-06 | 重复提交 | 同一草稿 | 连续点击提交两次 | 只生成一条记录（幂等） |
| E2E-07 | 重复地块 | 已存在同名同面积地块 | 再次提交 | 提示疑似重复，要求确认 |
| E2E-08 | 并发编辑 | 同一记录两个会话 | 同时修改并保存 | 后保存方收到冲突提示 |
| E2E-09 | 删除申请 | active 记录 | 发起删除申请 | 状态 delete_pending，审计留痕 |
| E2E-10 | 弱网重试 | 模拟超时 | 提交超时后重试 | 不产生重复记录，状态正确 |

## 五、执行方式

- **设计阶段**：对交互原型逐条走查 + 用例评审，确认流程与状态无缺口；
- **实现阶段**：用 Playwright/Cypress 在测试环境跑自动化 E2E，使用测试账号与测试数据；
- **证据**：录屏或截图、请求日志、审计记录；每次回归更新结果。

## 六、验收标准

- P0 用例 100% 通过；
- 无跨农户数据泄露；
- 重复提交与并发冲突均有明确处理；
- 每个状态跃迁都能在审计中查到。

## 七、不在本阶段

- 不招募真实农户、不做 10–20 户激活；
- 不追求交互视觉终稿；
- 不接入真实支付与物流。

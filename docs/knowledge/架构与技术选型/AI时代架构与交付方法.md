# AI 时代架构与交付方法（v0.1）

> 阅读顺序与权威优先级：见本目录《00 · 阅读顺序与权威优先级》；冲突时按该文裁决。

> 核心链路：**需求 → 数据结构 → 测试用例 → 业务逻辑 → AI 能力暴露 → E2E 验证**。
> 三条铁律：schema 先于代码；测试先于实现；AI 能力通过协议暴露，业务规则不写进 Prompt。

## 一、六步流水线

| 步骤 | 输入 | 产出 | 门禁 | 存放位置 |
| --- | --- | --- | --- | --- |
| 1 需求 | 场景、痛点、验收口径 | 需求卡 REQ-xxx | 需求评审通过 | 需求与沟通记录 |
| 2 数据结构 | 需求卡 | 领域对象、Zod schema、数据字典、迁移草案 | Schema 评审通过 | 数据与知识资产 |
| 3 测试用例 | 需求卡 + schema | Given/When/Then 用例（正常/异常/越权/并发/幂等） | 用例评审通过 | 测试与评测 |
| 4 业务逻辑 | schema + 用例 | 纯函数 domain + ports/adapters + 用例编排 | 测试全绿 | 代码仓库 |
| 5 AI 暴露 | 业务能力 | tool / skill / MCP / function calling + 契约卡 | 能力注册与权限评审 | 架构与技术选型 |
| 6 E2E 与评测 | 能力 + 用例 | Playwright E2E、AI 评测报告、审计记录 | 指标达标 | 测试与评测 |

> 顺序不可倒置。跳过第 2 步会导致字段漂移；跳过第 3 步会导致 AI 生成的代码无法验证。

## 二、需求 → 数据结构

1. 需求卡必须写清：谁在用、什么场景、输入输出、失败怎么办、验收口径；
2. 需求评审通过后才允许建 schema；
3. 一次只引入完成该需求所需的字段，禁止"顺手加字段"；
4. schema、数据字典、数据库迁移三处必须同时更新；
5. 先定义输入、输出、错误码，再写任何实现；
6. 用 2–3 条真实样例数据写进测试，作为 schema 的活文档。

## 三、函数式业务模块

- `domain/` 只放纯函数与类型，不依赖数据库、网络、框架；
- `application/` 编排用例，依赖通过参数注入；
- `adapters/` 实现 I/O（CloudBase、HTTP、存储）；
- `ui/` 只调用 application；
- 一个用例一个主函数，组合小函数；业务错误返回 `Result`；
- 单文件 ≤1000 行、单函数 ≤50 行、参数 ≤4（见《工程规范与AI编程约定》）。

## 四、业务如何融入 AI 架构

| 形态 | 用途 | 示例 | 约束 |
| --- | --- | --- | --- |
| Function calling | 模型调用内部函数 | `pest.detect`、`plot.submit` | 参数必须有 Zod schema；白名单 |
| Tool | 系统内原子能力 | 查询地块、创建订单草稿 | 经工具网关；审计与限额 |
| Skill | 打包的指令/流程/知识 | 「入库质检流程」「农技问答规范」 | 版本化；不直接访问数据；可组合 |
| MCP | 跨系统/第三方能力 | 神农 MCP、外部天气服务 | 网关代理；安全评审；数据边界 |

规则：

1. **业务先做成纯函数或 HTTP 接口，再暴露为 tool/skill/MCP**；不能把业务规则写进 Prompt；
2. 所有能力登记到**能力清单**：名称、版本、输入输出 schema、权限、限额、审计要求；
3. 模型只能看到 Agent 契约允许的工具列表，禁止全量暴露；
4. MCP 外部服务必须经网关代理，记录调用方、参数摘要与结果状态；
5. 能力变更遵循版本化与只增不删，废弃需标注。

## 五、测试先行（AI 编程稳定性的关键）

**顺序：用例 → 实现 → 测试代码。** 用例是规格，测试代码是执行器。

1. 用例用 Given/When/Then 写清前置、动作、预期；
2. 必测类型：契约（schema）、单元（纯函数）、E2E（主流程/异常/越权/并发/幂等）、AI 评测（golden set）、故障演练；
3. 用例变更视为需求变更，必须评审；
4. 测试数据使用固定夹具，不依赖生产数据与真实个人信息；
5. P0 功能没有用例不得实现；实现后测试不绿不得合并；
6. 对 AI 生成代码：先生成测试，再生成实现；人工重点审查用例是否覆盖边界，而不是只看代码是否能跑。

## 六、AI 编程稳定性清单

- 生成代码前先提供：需求卡、schema、用例、术语表、现有模块边界；
- 小文件、纯函数、显式类型、单一职责；
- 禁止隐式全局状态与跨层依赖；
- 每个模块必须有类型 + schema + 测试；
- 生成后依次跑：`tsc` → lint → 契约测试 → E2E → AI 评测；
- 测试失败先补用例，再改实现，禁止直接改断言迁就代码；
- 不引入元编程与自研 DSL。

## 七、完成定义（DoD）

- [ ] 需求卡与验收口径
- [ ] Zod schema + 数据字典 + 迁移
- [ ] 测试用例（正常/异常/越权/并发/幂等）
- [ ] 纯函数实现 + 单元测试全绿
- [ ] 能力注册（tool/skill/MCP）+ 契约卡
- [ ] E2E 通过 + AI 评测达标
- [ ] 审计事件与监测点
- [ ] 相关文档更新

## 八、反模式

- 先写代码后补测试；
- 业务规则写进 Prompt；
- 工具绕过网关直连；
- 字段随手加、同义词并存；
- 只测 happy path；
- 用生产数据做测试；
- 没有评测就上线。

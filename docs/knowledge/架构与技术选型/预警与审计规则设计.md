# 预警与审计规则设计（v0.2）

> 用“证据链”把 AI 预警做成可解释、可审计、可扩展的系统。
>
> 阅读提示：本文尽量不用术语。每个学术词第一次出现，都会用“大白话 + 生活类比”解释。只想看结论，读第 0、3、12 节。

## 0. 一句话

预警不是“AI 说有问题”，而是：

> **有人要证明一句话；系统帮他找证据、找缺口、催补证；最后人拍板，系统留痕。**

比如农户说“这批番茄可以按蔬菜上架”。这不是一个识别题，而是一个**要证明的主张**：

- 它是不是番茄？（识别）
- 在业务上算不算蔬菜？（分类口径）
- 数量、采收日期对不对？（表单证据）
- 质量检测有没有？（关键证据）
- 来源能不能追溯？（批次/溯源证据）

AI 可以帮忙看照片、查资料、找缺口；规则决定“缺什么算异常、多久算超时”；人决定“能不能上架”；审计记录“当时依据是什么”。

## 1. 三个真实问题，暴露了同一个根因

**问题一：当天上架就判“滞销”**

不是文案问题，是规则没有观察期。刚上架 20 分钟就报警，等于把“正常等待”当成“异常”。

**问题二：番茄算水果还是蔬菜**

植物学上番茄是果实；菜市场里它按蔬菜卖。模型如果按植物学回答“水果”，不是它笨，而是**业务分类口径没有告诉它**。这是“本体冲突”，不是“幻觉”。

**问题三：模型编造检测结果**

模型说“农残合格”，但根本没有检测报告。这不是分类问题，是**没有把话拴在证据上**。

三个问题的共同根因：

> 我们一直在问“模型，有没有问题？”，而不是问“**我们要证明什么？手上有哪些证据？还缺什么？**”

这份文档就是回答后面这个问题。

## 2. 先把学术词翻译成人话

| 学术词 | 大白话 | 生活类比 | 在本系统里是什么 |
| --- | --- | --- | --- |
| 主张 / 断言（claim / assertion） | 一句要被证明的话 | 病人说“我头疼”；农户说“这批番茄能上架” | 审核/质检要验证的业务目标 |
| 证据（evidence） | 能拿出来的材料 | 体温计、化验单、发票、照片 | 表单、图片、检测报告、批次记录 |
| 证据链 / 证据图（evidence chain / graph） | 把材料和结论连起来 | 医生把症状—检查—诊断串起来；会计把发票—合同—流水对上 | 支持/反驳/缺失三类关系 |
| 本体 / 分类词典（ontology / taxonomy） | 大家约定好的分类和叫法 | 菜市场的分类牌；植物学词典 | 番茄=蔬菜（业务口径）、别名、方言 |
| 接地 / 有据可依（grounding） | 每句话后面拴一张小票 | 不能空口说“我吃过饭”，要拿账单 | 结论必须引用证据 |
| 幻觉（hallucination） | 一本正经地编 | 医生编造一张没做过的化验单 | 模型编检测结果、产地、资质 |
| 溯源 / 出处（provenance） | 这条信息从哪来、谁给的、什么时候 | 小票上写医院、医生、时间 | 证据来源、采集时间、版本 |
| 主动感知（active perception） | 看不清就再凑近看一眼 | 医生觉得不放心，再加一个检查 | 发现缺口后主动补采 |
| 信息增益 / 信息价值（information gain / value of information） | 这次补采值不值得 | 这个检查能不能排除一个病，值不值这个钱 | 补证收益 vs 成本/时间 |
| 目标拆解 / 分层规划（goal decomposition / hierarchical planning） | 把大目标拆成小目标 | 办一桌饭拆成买菜、洗菜、炒菜 | “能上架”拆成品类、数量、日期、质量、溯源 |
| 充分性 / 适当性（sufficiency / appropriateness） | 证据够不够、靠不靠谱 | 办案：证据数量够不够，来源硬不硬 | 审计证据的数量与质量 |
| 校准（calibration） | 说 80% 准，就真的差不多 80% 准 | 天气预报说 80% 下雨，长期看确实约 80% | 模型置信度是否可信 |
| 漂移（drift） | 世界变了，旧经验不灵了 | 季节变了，去年的种植经验今年不一定适用 | 数据分布变化导致模型退化 |
| 人在回路（human-in-the-loop） | 关键一票由人拍 | 手术签字、贷款审批 | 高风险审核/质检 |
| 审计轨迹（audit trail） | 全程留痕的账本 | 银行流水，谁在什么时候做了什么 | 规则、模型、证据、人工决定 |
| 金标 / 真值（ground truth） | 后来确认的事实 | 病理报告确认是不是肿瘤 | 病害确诊、投诉成立、实际滞销 |
| 精确率 / 召回率（precision / recall） | 报的里面多少是真的；真的里面漏了多少 | 抓小偷：抓错几个 vs 漏掉几个 | 预警质量的核心指标 |
| 影子模式（shadow mode） | 新司机先坐副驾看，不实际开车 | 新规则先只记录，不真报警 | 上线前的安全验证 |
| 告警疲劳（alert fatigue） | 狼来了太多，人就不看了 | 一天 200 条报警，最后全点“知道了” | 预警过多导致失效 |
| 证据覆盖率（evidence coverage） | 需要的材料凑齐了几成 | 办证清单打了几个勾 | 已满足/必需证据总数 |

记住一句话：**这些词不是高深理论，只是把生活里的“查证”动作起了个学术名字。**

## 3. 一张图看懂整体设计

```text
货物/事件
   │
   ▼
① 看见（感知）────────────── AI/摄像头/语音/传感器
   │
   ▼
② 证据（可核实的材料）────── 图片、表单、检测报告、批次、历史记录
   │
   ▼
③ 规则（什么算异常）──────── 时间窗、阈值、升级、自动解除（传统代码）
   │
   ▼
④ 人（拍板）──────────────── 审核员/质检员/审计员
   │
   ▼
⑤ 审计（全程留痕）────────── 规则版本、模型版本、证据、决定
   │
   ▼
⑥ 评测（证明可信）────────── 金标、误报率、改判率、漂移
```

四句话分工：

- **AI 负责“看见和理解”**：从照片、语音、文本里提取证据；
- **规则负责“什么算异常”**：阈值、时间窗、级别、生命周期；
- **人负责“承担责任”**：高风险、冲突、低置信度；
- **评测负责“证明可信”**：AI 到底比纯规则好在哪里。

## 4. 规则引擎：先把“什么时候报警”说清楚

### 4.0 先有战略，才有阈值

规则不是中立的。24 小时还是 72 小时，不是技术常数，而是战略选择：

- 现金流优先 → 更早止损、更严升级；
- 农户信任优先 → 更重视回款、价格、申诉，而不是只盯转化；
- 食品安全红线 → 某些规则不允许自动放过；
- 单村密度阶段 → 规则奖励复购和质量，而不是盲目扩张；
- 风险胃口低 → warn 更早、critical 更严、人工闸门更多。

所以每条规则都应该写清楚 `strategyRefs`：它服务于哪个战略目标、受哪条风险预算/红线约束。  
**没有战略挂靠的阈值，只是拍脑袋；规则冲突，往往先要回到战略问“谁优先”。**

### 4.1 规则不是 if，而是一张表

一条规则至少包含：

| 字段 | 大白话 |
| --- | --- |
| `id` | 规则编号，比如 `listing.no_booking` |
| `version` | 第几版，审计要记 |
| `domain` | 属于哪个业务：审核/上架/派单/质检 |
| `entity` | 看哪个对象：货物/批次/订单 |
| `warnAfterMinutes` | 多久算“需关注” |
| `criticalAfterMinutes` | 多久算“高优先级” |
| `ownerRole` | 谁负责 |
| `suggestedAction` | 建议怎么处理 |
| `description` | 给人类看的规则说明 |

### 4.2 当前规则包（演示默认值）

| 规则 | 对象 | 需关注 | 高优先级 | 自动解除条件 |
| --- | --- | --- | --- | --- |
| 货物待审超时 | 待审货物 | 2 小时 | 8 小时 | 货物不再待审 |
| 批次上架后无订单 | 已上架批次 | 24 小时 | 72 小时 | 批次出现订单 |
| 订单生成后未派单 | 未派单订单 | 1 小时 | 4 小时 | 订单已有履约人 |

> 这些是预演默认值，正式版要接村规/政策配置。**阈值不是技术参数，是业务政策。**

### 4.3 告警的生命周期

```text
未触发 ──达到阈值──> open ──人确认──> acknowledged
                        │                 │
                        │                 └──条件升级──> open（升级重开）
                        └──条件解除────────> resolved
```

- **open**：待处理；
- **acknowledged**：人知道了，但问题不一定消失；
- **resolved**：条件解除，自动关闭；
- **升级**：从“需关注”到“高优先级”，已确认的会重新打开；
- **去重**：同一对象同一规则只保留一条活跃告警。

### 4.4 为什么要 `asOf`

`asOf` 就是“按哪个时间点来评估”。

- 当前时间扫描：刚上架 20 分钟，不报警；
- 模拟 24 小时后：才达到“上架无订单”的观察期；
- 模拟 72 小时后：升级为高优先级。

这就像“如果今天是明天，这份体检报告会怎么判”。**时间可以回放，但系统时间不用改。**

### 4.5 审计事件

| 事件 | 大白话 |
| --- | --- |
| `alert.scanned` | 这轮检查了什么、新增/更新/解除多少 |
| `alert.raised` | 哪条规则触发了，年龄多大 |
| `alert.escalated` | 从“需关注”升级到“高优先级” |
| `alert.resolved` | 条件消失，自动解除 |
| `alert.acknowledged` | 谁确认了 |

每条都带规则版本和评估时间。这样以后才能回答：“当时为什么报？按哪版规则报的？”

## 5. 证据链：怎么证明“这批货可以上架”

### 5.1 你提的 8 步，翻译成系统字段

| 你的说法 | 大白话 | 系统字段 |
| --- | --- | --- |
| 1 谁 | 这是哪件货/哪张图 | `subject` |
| 2 是什么 | 认出来是什么 | `entity` |
| 3 基础属性 | 它有哪些客观特征 | `attributes` |
| 4 延展意义 | 它和哪些知识/历史有关 | `associations` |
| 5 动机 | 它要满足什么业务目标 | `claim + subGoals + requiredEvidence` |
| 6 匹配 | 哪些证据支持/反驳/缺失 | `evidenceMap` |
| 7 求证 | 证据够不够 | `closure` |
| 8 未完成循环 | 缺什么、去哪补、什么时候停 | `loop` |

> 建议把“动机”改成“主张/目标”。对货物做心理动机归因，审计上既不可验证，也容易越界。我们真正要问的是：**这件货在当前业务目标下要证明什么？**

### 5.2 一个番茄的例子

**主张**：这批番茄可以按蔬菜上架。

**拆成子目标**：

1. 品类 = 蔬菜
2. 数量与申报一致
3. 采收日期有效
4. 质量检测合格
5. 来源/批次可追溯

**证据矩阵**：

| 子目标 | 支持证据 | 反驳证据 | 缺失 |
| --- | --- | --- | --- |
| 品类=蔬菜 | 业务词表 `produce-2026-10`：番茄=蔬菜 | 植物学词典：番茄=果实 | 业务口径已明确，按蔬菜 |
| 数量一致 | 表单 120kg、入库称重 120kg | 无 | 无 |
| 日期有效 | 采收 2026-10-19，不晚于今天 | 无 | 无 |
| 质量合格 | 无 | 无 | **检测报告** |
| 可追溯 | 批次 PC-…、溯源码 SY-… | 无 | 无 |

**结论**：4/5 满足，质量证据缺失。不能自动通过；要么补检测报告，要么转人工/质检站。模型不能因为“看起来新鲜”就代替检测。

### 5.4 每一步的“刹车”

没有刹车的循环很危险。第 8 步必须回答：

- **信息增益**：再补一次，能不能改变结论？
- **成本**：补证要花多少钱/多少时间？
- **深度**：最多追几层？
- **风险**：是不是高风险，必须直接转人工？
- **停止原因**：为什么停？是证据够了，还是不值得再查？

生活类比：医生不会为了一个感冒做全身 CT。**补证也要算性价比。**

## 6. 怎么把“证据够不够”打分

不要用模型自报的置信度当最终分数。建议看五个量：

| 指标 | 大白话 | 怎么算 |
| --- | --- | --- |
| 覆盖率 coverage | 必需证据凑齐几成 | 已满足子目标 / 必需子目标 |
| 一致性 consistency | 有没有互相打架 | 1 - 矛盾证据 / 证据总数 |
| 置信度 confidence | 证据本身有多确定 | 证据置信度的加权下限 |
| 权威度 authority | 来源硬不硬 | 政策/检测报告 > 表单 > 模型推断 |
| 时效 freshness | 证据新不新 | 按业务有效期衰减 |

一个可用的总分：

```text
score = 0.35*coverage
      + 0.25*consistency
      + 0.20*confidence
      + 0.15*authority
      + 0.05*freshness
```

判定可以很朴素：

- 覆盖率 100%、无矛盾、关键证据达标 → 自动通过（低风险）；
- 缺关键证据或分数在中段 → 转人工/补采；
- 出现矛盾或低于底线 → 驳回/升级；
- 高风险品类 → 无论分数多高，都保留人工闸门。

这套思路和会计审计里的 **ISA 500** 很像：证据要“充分”（数量够）且“适当”（相关、可靠）。我们只是把它变成了可计算的字段。[ISA 500 参考](https://www.icjce.es/images/pdfs/tecnica2/normativainternacional/isa500.pdf)

| 证据链接的正式论证 | Evidence-linked argument | 把结论和证据写成可检查的结构 | [Evidence-Linked Formal Arguments](https://arxiv.org/html/2604.04103) |

### 客观定位

- **作为系统设计：偏先进。** 多数企业还停留在“模型打分 + 阈值 + 弹窗”，你的“目标—证据—缺口—补证—闭合”更完整。
- **作为学术研究：集成型工作。** 组件都有前人研究，整合到农业/货物审计场景有价值，但不是新算法。
- **作为工程实现：早期。** 还缺正式 schema、出处模型、停止理论、评测基准。
- **最有可能的研究切口：** 面向农产品/食品溯源的“审计证据链补全”基准：给定主张和一组多模态证据，系统判断证据是否充分、缺什么、去哪补、何时停。这个方向目前还比较空白。

## 8. 评测中心：怎么证明 AI 值得信任

### 8.1 它放在哪

```text
运行链路：
业务事件 → 规则引擎 → 预警 → 人/审计
              ↑
       AI 证据（模型输出）

离线链路：
审计事件 + 人工决定 + 真实结果（金标）
              ↓
        独立评测中心
  精确率/召回率、误报率、漂移、改判率、成本
              ↓
  模型/提示词/规则版本的发布门禁
```

它**不放在模型里，也不放在触发链路里**。它是独立的“评测与治理域”。

### 8.2 大白话

- **金标** = 后来确认的事实，像考试标准答案；
- **精确率** = 报的 10 条里几条是真的；
- **召回率** = 真的 10 条里报出来几条；
- **人工改判率** = 人把 AI 结论改掉的比例；
- **校准** = 模型说 80% 准，长期看是不是真的 80%；
- **漂移** = 世界变了，模型没跟上；
- **告警疲劳** = 一天报太多，人反而不看；
- **影子模式** = 新规则先只记录、不真报警，像新司机先坐副驾。

### 8.3 评什么

| 指标 | 回答什么问题 |
| --- | --- |
| Precision / Recall | 报得准不准、漏得多不多 |
| False positive rate | 误报多不多 |
| Human override rate | 人改判多不多 |
| Calibration | 置信度能不能信 |
| Drift | 模型是不是过期了 |
| Alert fatigue | 人会不会被淹没 |
| Cost per true alert | 每条真预警花多少钱 |
| Time-to-detect | 多快发现 |

### 8.4 怎么评

1. **金标集**：确认过的病害、质量事件、真实滞销、投诉成立；
2. **回放**：历史数据重跑旧规则/新规则/AI；
3. **影子模式**：AI 只记录，不触发；
4. **对照**：AI vs 纯规则基线；
5. **分组评估**：把评估结果按品类、村组、季节、风险等级分组，分别算指标——像体检报告按科室分开看，而不是只看一个总分。这样能发现“总体 90 分，但番茄只有 60 分”的问题。
6. **发布门禁**：只有明显优于基线，且没有不可接受的告警疲劳，才上线。

## 9. 规则会变：怎么持续维护、又不互相打架

这是这套系统最难的部分，而且**不是“让 AI 自己学习”就能解决**。

### 9.1 先分清三种变化

| 变化类型 | 例子 | 谁能改 | 怎么改 |
| --- | --- | --- | --- |
| 事实变化 | 价格、天气、库存、虫情 | 数据/业务系统 | 自动刷新数据、更新模型 |
| 规则变化 | 政策、村规、市场规则、阈值 | 规则所有者/治理小组 | 提案 → 评审 → 生效 → 回放 |
| 判断变化 | 个案例外、人工改判 | 审核员/审计员 | 记录理由 → 复核 → 反馈，不静默改规则 |

一句话：**事实可以自动更新，规则不能自动改，判断要留理由。**

### 9.2 规则要有“身份证”

同一条“上架无订单”，叶菜可能 12 小时就该提醒，根茎可以等 48 小时，某村旺季又可能放宽到 72 小时。  
这不是“规则冲突”，而是**规则的范围不同**。所以每条规则都要写清楚：

```json
{
  "id": "listing.no_booking",
  "version": 2,
  "status": "active",
  "scope": {
    "role": "keeper",
    "object": "batch",
    "region": "village-xinglonggou",
    "category": "叶菜"
  },
  "authority": "village_policy",
  "strategyRefs": ["objective.trust", "risk_budget.cash"],
  "precedence": 3,
  "effectiveFrom": "2026-10-20",
  "effectiveTo": null,
  "sourceDocument": "村委2026-10号公告",
  "owner": "village-committee",
  "approver": "audit-board",
  "warnAfterMinutes": 720,
  "criticalAfterMinutes": 1440,
  "tests": ["golden-listing-leafy-001"]
}
```

字段的大白话：

- **scope**：管谁、管什么、管哪个村、管哪个品类；
- **authority**：这条规则是谁定的（法律/政策/村委/市场惯例）；
- **strategyRefs**：它服务于哪些战略目标、受哪条风险预算/红线约束；
- **precedence**：打架时谁优先；
- **effectiveFrom / effectiveTo**：从哪天生效、到哪天失效；
- **sourceDocument**：依据哪份文件；
- **owner / approver**：谁提、谁批；
- **tests**：这条规则的金标用例。

### 9.3 冲突怎么处理

规则冲突一般不是“谁对谁错”，而是**优先级和范围没写清楚**。可以先定一个裁决顺序：

1. **权威级别**：法律 > 上级政策 > 县级 > 村级 > 市场惯例 > 默认值；
2. **具体程度**：专门规则 > 通用规则；
3. **时间**：新生效规则 > 旧规则，但要注意过渡期和老规则保护；
4. **范围**：局部例外只在它声明的范围内生效；
5. **仍然无法裁决**：转人工治理小组，不让模型拍脑袋。

常见冲突：

- 同一个对象，不同阈值；
- 同一个阈值，不同角色；
- 生效时间重叠；
- 番茄/西红柿、斤/公斤这类名称和单位不一致；
- 规则之间循环依赖。

工程上可以做自动检查：阈值比较、时间重叠、别名归一、单位统一、依赖环检测。  
但“谁优先”是业务决定，不是算法决定。

### 9.4 规则变更流程

```text
发现变化（政策/市场/事故/反馈）
  → 起草变更（AI 可以帮忙摘要、对比、生成测试）
  → 影响分析（影响哪些规则、案件、看板、Agent）
  → 冲突检查（阈值/时间/范围/别名）
  → 回放与影子运行（历史数据 + 新旧规则对比）
  → 人工评审与批准（业务 + 审计）
  → 灰度生效（canary）
  → 监控（误报/漏报/改判/投诉）
  → 回滚或正式退役
```

每一步都要留痕：谁提的、依据什么、影响了什么、测试结果、谁批的、什么时候生效。

### 9.5 AI 能做什么，不能做什么

**AI 可以帮忙：**

- 监测新政策、新市场信息；
- 对比新旧规则差异；
- 检测潜在冲突；
- 做影响分析；
- 生成/补充测试用例；
- 找出长期没被触发或已经过期的规则；
- 聚类人工改判和投诉，发现规则不合理的地方。

**AI 不能做：**

- 静默改阈值；
- 自己批准自己的变更；
- 裁决价值冲突（比如“效率优先还是公平优先”）；
- 决定法律/政策的优先级；
- 把人工改判直接当成正确答案（人也会错，也可能有偏见）。

所以“AI 自我学习”在规则层要改成：

> **AI 学习的是“提出变更建议 + 证据 + 影响”，不是“悄悄改规则”。**

模型学习（识别更准）和规则学习（规范怎么定）是两件事：

| 类型 | 学什么 | 怎么更新 | 谁负责 |
| --- | --- | --- | --- |
| 模型学习 | 图片/语音/文本的识别能力 | 训练、评测、灰度 | 算法团队 |
| 规则学习 | 阈值、范围、优先级、政策口径 | 提案、评审、生效、回放 | 规则所有者 + 治理小组 |

### 9.6 多角色、多对象、多地区

同一个词，在不同角色和范围下含义不同：

| 场景 | 规则范围 | 可能阈值 |
| --- | --- | --- |
| 叶菜上架 | 品类=叶菜 | 12h / 24h |
| 根茎上架 | 品类=根茎 | 48h / 96h |
| 某村秋收旺季 | 村=兴隆沟，季节=秋收 | 72h / 144h |
| 全县默认 | 无特殊范围 | 24h / 72h |

角色也一样：

- 农户看到“能不能提交”；
- 入库员看到“能不能审核/上架”；
- 审计员看到“能不能核查/追责”；
- 管理员看到“全局状态”。

**同一件货，不同角色看的是不同规则，不是同一套阈值。** 这些都要写进 scope，不能靠口头约定。

### 9.7 工程落地

- **规则注册表**：规则 ID、版本、状态、范围、权威级别、生效时间、来源文件、负责人、审批人；
- **规则 DSL / JSON**：可执行、可测试、可 diff；
- **冲突检查器**：阈值、时间、范围、别名、单位、依赖环；
- **影响分析**：这条规则改了，会影响哪些案件、看板、Agent、通知；
- **回放与影子**：历史数据重跑，新旧规则对比；
- **审批与回滚**：提案人、评审人、批准人分离；
- **规则中心 UI**：看范围、生效时间、差异、冲突、回放结果；
- **审计事件**：`rule.proposed / approved / activated / deprecated / rolled_back`；
- **指标**：冲突数、过期规则数、变更周期、人工改判率、误报/漏报。

当前 demo 只有单版本规则包，还没有规则注册表、变更审批、冲突检测和生效时间。这部分要在“规则会变”之前先补上。

### 9.8 一句话

> **规则治理不是“让 AI 自己学”，而是“AI 帮忙发现变化、起草变更、检查冲突、评估影响；人批准，系统版本化，历史可回放”。**

### 9.9 电车难题：有些冲突不是技术问题

规则冲突至少有三层：

| 冲突类型 | 例子 | 能不能靠技术解决 |
| --- | --- | --- |
| 技术冲突 | 阈值重叠、单位不一致、别名不一致 | 可以，工程能修 |
| 政策冲突 | 不同部门/角色的优先级不同 | 需要合法的裁决机制 |
| 价值冲突 | 谁承担代价、谁受益、什么更重要 | **没有中立算法，只有合法程序和责任** |

电车难题的关键不是“1 个人 vs 5 个人”的算术，而是：

- 谁有权扳道岔？
- 谁承担后果？
- 是作为还是不作为？
- 信息是否确定？
- 有没有第三种选择？

放到这个系统里：

- 降低“滞销”阈值 → 干预更多，可能浪费人力、误伤农户；
- 提高阈值 → 农户可能承担更大损失；
- 拒绝一批货 → 农户承担成本；放行 → 消费者承担风险。

这些不是调参，是价值排序。

**系统应该做的：**

1. 把取舍摆出来：谁受益、谁受损、代价是什么、不确定性多大；
2. 明确谁有权决定：法律、村委、治理委员会、听证，不是模型或工程师；
3. 记录理由、反对意见、审批人；
4. 给受影响方申诉和复核渠道；
5. 优先可逆、渐进、可补救的动作（先抽检、先暂扣、分批处理），而不是一上来就不可逆；
6. 高风险、不可逆、涉及基本权利的决定保留人工闸门；
7. 设定红线：哪些决定不允许全自动。

**AI 能做的：**

- 算混淆矩阵、期望损失、分组影响；
- 模拟不同阈值下谁受益、谁受损；
- 把选项和后果讲清楚。

**AI 不能做的：**

- 替社会决定“谁更重要”；
- 用“模型置信度”冒充道德合法性；
- 把价值权重藏进代码。

“客观评估”不是“价值中立”。它应该公开：

- 用了什么价值权重；
- 谁选的；
- 对哪些群体有什么影响；
- 有没有申诉和复核。

一句话：

> **工程能减少电车难题的发生频率，但不能替社会做选择。**

## 10. 当前 demo 已经做到哪、还差什么

### 已经做到

- 规则包 `2026-10-19.1`：三条规则、时间窗、升级、自动解除；
- `asOf` 模拟时间：当前 / 1 小时后 / 24 小时后 / 72 小时后；
- 告警生命周期与审计事件：`scanned / raised / escalated / resolved / acknowledged`；
- UI 规则面板：阈值、责任角色、建议动作；
- 人类可读告警：品种、批次、订单、年龄、观察期、建议；
- 单元测试 12 条通过：未到观察期、warn、critical、升级、去重、自动解除。

### 还没有做到

- **完整的证据链 schema 和评分**：当前审核建议还是简化版；
- **多模态输入**：没有图片识别、语音转写、巡检文本；
- **业务本体/词表**：当前品类判断还是正则占位（茶/果/粮/肉…），番茄/黄瓜/茄子会暴露问题；
- **出处模型**：没有 W3C PROV 级别的证据来源记录；
- **评测中心**：没有金标集、误报率、校准、漂移；
- **规则治理**：没有规则注册表、变更审批、冲突检测、生效/失效时间、回滚；当前规则包是单版本；
- **战略挂靠**：规则阈值未挂靠战略目标/风险预算；规则面板只显示阈值、责任人和建议，不显示“为什么是这个阈值”；
- **业务日历/通知/规则后台**：阈值仍是演示默认值；
- **本地/云端规则包各一份**：生产应抽成共享版本化配置。

## 11. 下一步建议

1. **把证据链固化成 schema**：`claim → subGoals → evidenceMap → closure → loop`；
2. **建规则注册表和变更流程**：范围、权威级别、生效时间、冲突检查、审批、回放、回滚；
3. **给每条规则加 `strategyRefs`**：在规则面板显示它服务于哪个战略目标/风险预算，避免“拍脑袋阈值”；
4. **建版本化农产品词表**：番茄/黄瓜/土豆/辣椒、别名、方言、业务口径；
5. **先做一个高价值多模态场景**：病虫害照片或老人语音，不要一次铺开；
6. **用价值-of-information 定义停止**：补证收益、成本、深度、风险；
7. **建独立评测中心**：金标、影子模式、回放、校准、改判率；
8. **对齐 ISA 500 / NIST AI RMF / ISO/IEC 42001** 的 assurance 语言；
9. **保持规则引擎**：AI 不直接触发高风险告警，必须经过规则 + 人工闸门；
10. **如果要研究**：做“农产品审计证据链补全”基准，而不是再做一个识别模型。

## 12. 一页总结

**8 步的大白话：**

> 看见 → 认出 → 查属性 → 联想 → 定目标 → 对证据 → 补缺口 → 闭环。

**四句话分工：**

> AI 提议，规则裁决，人类担责，评测证明。

**四个不要：**

- 不要让 AI 自己定义“番茄是什么”；业务词典说了算；
- 不要把模型置信度当成评测结果；要用真实结果对齐；
- 不要无限循环补证；要有收益、成本、深度和风险刹车；
- 不要把价值冲突藏进阈值；谁承担代价必须可见、可申诉、可追责。

**四个一定要：**

- 规则、词表、模型、提示词都要版本化；
- 每条结论都要能追溯到证据和出处；
- 高风险/冲突/低置信度一定留人工闸门；
- 规则变更要有人批准、有生效时间、可回放、可回滚。

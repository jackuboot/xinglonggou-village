# 00 · 阅读顺序与权威优先级（v1.1）

> 给人类与编程 Agent 的入口。**先读本文，再按顺序读其他文档；冲突时按本文裁决，不要自行猜测。**
> 本目录回答"怎么建、用什么、怎么测"；"做什么"以需求与蓝图为准。

## 一、按任务的阅读顺序

### A. 首次上手（约 30 分钟）

1. 本文件；
2. 《AI 时代架构与交付方法》——交付流水线；
3. 《技术选型与资源登记》——语言、框架、运行时、ADR；
4. 《工程规范与 AI 编程约定》——命名、字段、错误码、模块化；
5. 《接口规范与业务边界》——云函数、外部 REST、MCP 的范围与规范；
6. 《开放决策处理记录》——已关闭与未关闭的决策；
7. 《容量、稳定性与成本预演》——档位、SLO、成本假设。

### B. 实现一个需求（每次开发都按此顺序）

1. **范围**：需求基线中的 REQ-xxx + 蓝图对应章节（目标与验收口径）；
2. **数据**：数据字典 + Zod schema + 迁移草案（数据与知识资产）；
3. **测试**：P0 评测方案 + 对应 E2E 用例（测试与评测）；
4. **规则**：工程规范（命名/字段/错误码/函数式/模块上限）；
5. **接口**：按《接口规范与业务边界》确认属于云函数/HTTP/MCP 的哪种范围与暴露面；
6. **决策**：技术选型 ADR + 开放决策（确认没有冲突）；
7. **实现**：纯函数 `domain` → `adapters` → `application`；
8. **AI 暴露**：tool / skill / MCP 注册 + Agent 契约卡；
9. **验证**：E2E + AI 评测 + 审计事件；
10. **发布**：部署手册 + 阶段门禁。

### C. 架构变更

1. 先查《开放决策处理记录》是否已有结论；
2. 再查《技术选型与资源登记》的相关 ADR；
3. 用《容量、稳定性与成本预演》判断是否触发升级；
4. 用《工程规范》确认约束；
5. 变更完成后回写文档、ADR 与决策记录。

| 文档 | 回答什么 | 权威性 | 备注 |
| --- | --- | --- | --- |
| 00 阅读顺序（本文） | 先读谁、冲突听谁 | 导航，无技术裁决权 | 其他文档冲突时用本文规则 |
| AI 时代架构与交付方法 | 交付顺序与方法 | 流程权威 | 规定"先 schema、先用例" |

| 开放决策处理记录 | 已关闭/未关闭的具体决策 | **最新决策权威** | 优先于旧文档表述 |

| 测试用例 / 评测方案（测试与评测） | 验收标准 | **验收权威** | 不得改断言迁就实现 |
| 蓝图 / 需求基线 | 做什么、范围与优先级 | **范围权威** | 架构文档不能自行扩大范围 |

## 三、冲突裁决顺序（从高到低）

1. **用户的最新明确决定**（含《开放决策处理记录》中已关闭的 D-xx）；
2. **范围与验收**：蓝图、需求基线、测试用例；
3. **技术选择**：技术选型中的 ADR；
4. **编码规则**：工程规范；
5. **交付流程**：AI 时代架构与交付方法；
6. **容量与成本假设**：容量预演（仅参考，实测优先）。

具体规则：

- 同一主题有多个版本时，**最新版本优先**；历史版本归档中的内容只用于追溯；
- 字段冲突以数据字典 + Zod schema 为准；
- 测试预期冲突以用例为准，禁止改断言迁就代码；
- 两个文档冲突且无法裁决时：**停止实现**，把冲突写入《开放决策处理记录》，等确认后再继续；
- 任何架构调整必须回写文档，禁止代码与文档双轨。

## 四、版本与过期判断

- 本地文件名不含版本；QMind 标题带 `vX.Y`；以最新版本为准；
- 「历史版本归档」目录中的文档**不作为实现依据**；
- 标注"待校准 / 假设 / 规划"的数字，不得当作承诺或验收标准；
- 看决策时优先查《开放决策处理记录》与 ADR 的变更记录，而不是旧章节描述。

## 五、实现前检查清单（Agent 必读）

- [ ] 已读 REQ 与验收口径；
- [ ] 已读数据字典与 schema；
- [ ] 已读对应 E2E 用例；
- [ ] 已确认没有未关闭的 D-xx；
- [ ] 已确认运行时/模型与 ADR 一致；
- [ ] 新增字段、工具、错误码已登记；
- [ ] 已准备测试数据与回滚方案。

## 六、禁止事项

- 只读一个文档就开始写代码；
- 引用历史版本归档中的旧决策；
- 把容量假设当作承诺；
- 改断言迁就实现；
- 代码与文档不一致却不回写；
- 新增字段/工具不留登记。
